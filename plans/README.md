## Findings considered and rejected (do not re-audit)

- **`workflow_dispatch` on release-publish.yml as a review bypass**: deliberate single-maintainer escape hatch; the workflow runs the full lint/typecheck/test/build gate before publishing. Revisit only if the maintainer count grows.
- **Non-null assertions on resolved target lookups** (`src/context/user-command.ts:28`, message-command equivalent): Discord's API contract guarantees the resolved entry for `target_id` on context-menu interactions; the `!` encodes that contract.
- **Peer range `>=3.0.0-dev` on discord.js packages**: inherent to building against pre-release upstream; Renovate + CI already catch drift on discore's side; consumers can pin. No actionable fix until discord.js v3 stabilizes — then peers, README, and AGENTS.md need one coordinated bump.
- **Direct unit tests for `createEventContext` and `src/routing/shared.ts` helpers**: trivially covered through router and integration tests; standalone tests would assert property assignments.
- **Consolidating the nine `defineX` factories behind a shared schema**: premature abstraction for a stable surface; revisit only when a cross-cutting definition feature (validation, metadata) actually lands.
- **Type-level tests for the reply/defer state machine**: runtime tests (plans 002/006) cover the invariants; the state is closure-internal, not type-encoded.
- **Standalone CONTRIBUTING.md**: solo-maintainer project; a Development section in the README (plan 003, step 5) covers the real need.
- **Integration tests asserting full reply payloads** (not just call counts): worthwhile polish but marginal next to the above; fold into future test work if payload bugs actually surface.
- **`softprops/action-gh-release@v3` pinned by tag rather than SHA**: noted; third-party action in a release workflow is the one place SHA-pinning pays — one-line change the maintainer can make without a plan.
- **errorResponse functions can leak error details to end users**: default response is a safe generic; custom functions are explicit opt-in. The README error-handling paragraph added by plan 001 is the right place if the maintainer wants a warning sentence.
